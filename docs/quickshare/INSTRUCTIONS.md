# 指示書 1/2: Clipshare 改修（Next.js / Prisma / NextAuth）

> 取り込み補足: 本ファイルは作業パックに合わせて配置済み。実装順・自走ルールは `CLAUDE.md` と `PROGRESS.md` を優先する。

対象リポジトリ: https://github.com/choko1229/clipeshare
目的: Windows クライアント「Clipshare Quick」（VRChat 写真の自動アップロード＆共有URL発行）のために、トークン認証API・関連画面・上限設定を追加する。**この指示書を先に実装する。**
参照: 仕様書Doc「VRC写真共有ツール 仕様書（Clipshare連携）」、UIデザインキャンバス（Web画面は 01・07・13・17・20）。

## 0. 進め方の前提（必ず守る）

- 不明点・仕様の穴を見つけたら、**実装せず質問する**。推測で決めない。
- 既存の Web 側（Cookie セッション経由）の挙動は**変えない**。回帰させない。
- 設定値で DB 管理できるものは DB に置き、WebUI（管理画面）から変更可能にする。`.env` は最小限。
- API と UI を明確に分離する（`/api/v1/*` は純粋な API、画面は別ルート）。
- TypeScript は `strict`。`any` 禁止。入力は zod 等で検証。
- エラー処理・例外処理・詳細ログを実装する。**ログにトークン、Authorization ヘッダ、ファイルの中身を出さない。**
- セキュリティ最優先（本書 §7）。
- 完了後、本書 §9 のセルフレビューを**複数回**行い、結果を報告する。

## 2. 現状（確認済み。実装前にコードで再確認すること）

- Next.js（App Router）、Prisma（MySQL）、NextAuth（Discord / X / Email）、sharp、nanoid。
- `QuickShare` モデル: `publicId`(nanoid(10))、`deleteToken`、kind(IMAGE/VIDEO)、status(PROCESSING/READY/FAILED)、`expiresAt`、`userId`、`ipHash`。
- 現行アップロード: `POST /api/qick/upload`（セッションCookie認証のみ）。
- 共有URL: `/q/{publicId}`。HTML を求めると `/q/{id}/view` へリダイレクト、それ以外はファイル直返し。閲覧ページに OGP なし（noindex のみ）。
- 既定値: 画像 20MB、動画 200MB、保存 24 時間、匿名 1日5件。ログイン中の上限は AccountLevel 別。
- 画像処理: 回転補正 → 長辺 2000px 縮小 → 下部に広告バナー合成 → WebP(q88)。
- 削除: セッション所有者 or Cookie の deleteToken のみ。
- Discord ボット用ルートは `Authorization: Bearer <secret>` 方式（参考パターン）。
- **「1日の上限」の数え方は現行の実装に合わせる**（コードを読んで確認し、同じ関数・同じ基準を再利用。数え方を新設しない）。

## 3. 実装順と内容

### Step 1: DB（Prisma）
- 新モデル `ApiToken`:
  - `id`, `userId`(FK), `name`（端末名。クライアントが送る PC 名等、最大長制限）, `tokenHash`（SHA-256 など。**元の値は保存しない**）, `prefix`（先頭数文字。一覧での識別用。ハッシュ照合用ではない）, `createdAt`, `lastUsedAt`, `lastUsedIpHash`, `revokedAt`(nullable)。
  - **期限なし（失効するまで有効）**。**端末数の上限なし**。
  - インデックス: `tokenHash` unique、`userId`。
- AccountLevel にツール用の上限列を追加（値 `0` = 無制限）: 例 `toolImageMaxMB`, `toolVideoMaxMB`, `toolDailyLimit`。
  - **既定値は現行のログイン上限をそのまま引き継ぐ**（マイグレーションで既存レベルの現行値をコピーする）。
- 画像上限の既定 20MB → 50MB（既存設定の変更。DB設定なら値更新、定数なら設定化）。
- 認可フロー用の一時データ（認可コード/接続コード）: 短命（例 10 分）、使い捨て、ハッシュ保存。テーブルまたは既存の VerificationToken 流用のどちらが保守的か検討し、**方針を質問・提示してから**実装。

### Step 2: 認可フロー（ブラウザ認可）＋トークン発行  〔画面 07 / 13〕
方式（案）: ループバック + PKCE。**NextAuth との統合方法は未設計。実装前に設計案を提示して承認を得る。**
- クライアントが `code_challenge` と `redirect_uri=http://127.0.0.1:<port>/callback`（loopback のみ許可、ポートは任意）、`state`、端末名を付けて認可画面（例 `/qick/authorize`）を開く。
- 認可画面（画面 07）: 未ログインなら既存ログインへ（ログイン後に戻る）。ログイン後、**接続コード（例 `7K2-M9Q`）を表示**し、クライアント側表示と照合してもらう（フィッシング対策）。「許可」「キャンセル」。
- 許可すると一時コードを発行し、`redirect_uri` へ 302（`code`, `state`）。クライアントが `POST /api/v1/auth/token`（`code`, `code_verifier`）でトークンを受け取る。トークンは**この応答でのみ平文を返す**。
- 検証: `redirect_uri` は loopback（`127.0.0.1` / `[::1]`）のみ。`state` 必須。コードは使い捨て・期限・端末名の長さ制限。PKCE `S256` 必須。
- 連携アプリ管理（画面 13）: ログイン中ユーザーが自分のトークン（端末名・作成日・最終使用・先頭文字）を一覧し、**端末ごとに失効**。
- 失効 API: `DELETE /api/v1/auth/token`（クライアントが自分自身を解除。アンインストール時用）。

### Step 3: アップロード/削除 API  〔`/api/v1/*`〕
- `POST /api/v1/quick`（multipart）
  - 認証: `Authorization: Bearer <token>`。無し → **匿名扱い**（バナーあり、1日5件、現行と同じ IP ハッシュ方式）。**無効/失効トークンは匿名にフォールバックせず 401**（意図しない匿名公開を防ぐ）。
  - パラメータ: `file`、`quality=original|shrink`（既定 shrink）。
  - バナー: **API 経由のみ分岐**。トークンあり＝バナーなし、匿名＝バナーあり。Web 経由の挙動は不変。
  - 画質: `original` = 高品質 WebP 再エンコード、メタデータ（EXIF/位置情報等）除去、バナー無し。`shrink` = 長辺 2000px（現行と同じ）。**メタデータ除去が sharp の既定で成立するかは未検証 → 実画像でテストして確認**（`withMetadata()` を呼ばない／`rotate()` 後の向き保持を確認）。
  - 上限: AccountLevel のツール用上限を適用（0=無制限）。超過時は **HTTP 413 とエラーコード（`SIZE_LIMIT_EXCEEDED`）、上限値**を返す（クライアントが画像を自動縮小して再送、動画はエラー表示するため、コードで判別できること）。日次上限超過は **429 `DAILY_LIMIT_EXCEEDED`** と次回リセット時刻。
  - 動画: **現行の変換処理をそのまま使う**。拡張子だけでなく**マジックバイトで種類を検証**し偽装を拒否。
  - レート制限: **トークンごと**（匿名は IP ハッシュ）。`429` と `Retry-After`。
  - 応答（JSON）: `id(publicId)`, `url`（`/q/{id}` の絶対URL）, `deleteUrl` もしくは削除可能であることの情報, `kind`, `expiresAt`, `status`。**クリップボードに入れる URL は `/q/{id}`**。
- `DELETE /api/v1/quick/{id}`: トークンの所有者のみ削除可能。他人のIDは 404（存在を漏らさない）。匿名アップロードは deleteToken を応答に含め、それを提示すれば削除可。
- エラー応答の形式を統一（`{ error: { code, message } }`）。内部情報（スタックトレース、パス）を返さない。

### Step 4: OGP・共有ページ  〔画面 17〕
- `/q/{id}/view` に OGP / Twitter Card メタデータを追加（`og:title`, `og:image`(画像サムネ or 動画ポスター), `og:type`, `twitter:card`）。現状の `noindex` は維持（検索エンジンには出さない）。
- **Discord / X での表示は未検証 → 実際にリンクを貼って確認**（本番相当環境、公開URLで）。動画の `og:video` 扱いも検証し、無理なら静止画ポスターで代替。

### Step 5: 管理画面  〔画面 20〕
- 管理画面の AccountLevel 設定に、ツール用上限（画像MB/動画MB/日次件数、0=無制限）を追加（DB管理、WebUIで変更）。
- **トークン管理（管理者）**: 管理者が他ユーザーのトークンを**一覧（値は非表示、prefix・端末名・最終使用のみ）**で確認し**失効**できる。操作は監査ログに残す（誰が・誰の・どのトークンを・いつ）。
- ※ このトークン管理の画面デザインは未作成。既存の管理画面トーンに合わせて実装し、**実装前に画面案をテキストで提示**。

### Step 6: ダウンロードページ  〔画面 01〕
- `/qick/download`（公開、ログイン不要）。内容: アプリ名「Clipshare Quick」、最新バージョン、インストーラーのダウンロード、更新履歴、署名/信頼手順（自己署名の間）、動作環境。
- ダウンロード元は GitHub Releases の最新リリース。**GitHub API は未認証で 1 時間 60 リクエスト（IPごと）。サーバー側でキャッシュ（例 10 分〜1時間、ISR/メモリ/DB）**し、失敗時は最後に成功した結果を表示。リリース情報（バージョン、サイズ、署名フィンガープリント、リリースノート）を DB設定 or 取得結果で表示。
- クライアントの更新確認用エンドポイント（任意）: `GET /api/v1/client/latest` でも同じキャッシュを返す（クライアントが GitHub API を直接叩く回数を減らすため。採用可否は質問）。

- 認証失敗の連続はレート制限＋警告ログ。

## 7. セキュリティ要件
- トークンは十分なエントロピー（32 バイト以上の乱数、URL-safe）。DB は**ハッシュのみ**。比較は定数時間。
- 認可: `redirect_uri` は loopback 限定、`state`/PKCE 必須、接続コード表示、コード使い捨て・短命、CSRF 対策（認可画面の「許可」は POST + CSRF トークン）。
- 他人のリソースへのアクセスは 404（列挙防止）。管理者操作は権限チェックと監査ログ。
- アップロード: サイズ上限を**ストリーミング中に強制**（全文メモリ展開しない）、MIME はマジックバイト検証、巨大画像のピクセル数上限（decompression bomb 対策。sharp の `limitInputPixels` を確認）、ファイル名は信用しない（保存名は publicId）。
- レスポンスヘッダ・CORS: `/api/v1/*` は不要なオリジンを許可しない。
- 失効したトークンの即時拒否。ログイン解除/アカウント削除時のトークン連動失効。

## 8. テスト（自動 + 手動）
自動テスト（境界値重視）:
- 認証: トークンなし→匿名、有効→成功、失効→401、他人のトークンで他人のリソース削除→404、不正形式→401。ログにトークンが出ない。
- 認可フロー: PKCE 不一致、`state` 不一致、期限切れコード、使い回しコード、非 loopback の `redirect_uri` が拒否される。
- バナー: トークンあり=なし、匿名=あり、Web 経由=従来どおり。
- 上限: レベル別上限、`0`=無制限、上限ちょうど/+1 バイト、匿名 5 件目/6 件目、日次リセット境界（現行の数え方と一致）、413/429 の本文とコード。
- 画像: `original`/`shrink`、EXIF 除去（位置情報付きサンプルで確認）、回転補正、巨大画像でメモリが膨らまない。
- 動画: 偽装ファイル（拡張子のみ動画）拒否、大容量の安定受信、現行変換が従来どおり動く。
- レート制限、OGP メタ出力、ダウンロードページのキャッシュ（GitHub API 失敗時のフォールバック）。
手動確認（本番相当）:
- Discord / X で `/q/{id}` を貼ってプレビュー表示。
- ライト/ダーク、日本語表示崩れなし、連携アプリ管理で端末ごとの失効が即時反映。
- 管理者のトークン一覧が値を出さず、失効できる。
