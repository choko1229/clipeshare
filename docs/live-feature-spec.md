# ライブ配信機能 仕様書(Phase 1: Web配信・視聴)

`docs/live-feature-feasibility.md` の調査結果を受けて、ユーザーとの対話で決定した仕様をまとめる。Web配信・視聴(レイヤーA)に加え、VRChatからの視聴に必要な最小限の出力(レイヤーBの一部、13章)も本仕様に含む。

## 1. ページ構成・ルーティング

| パス | 内容 | 認証 |
| --- | --- | --- |
| `/live` | 自分専用の配信管理ページ。OBSへの入力案内(ストリームサーバーURL・ストリームキー)、配信プレビュー、配信on/off、ストリームキー再発行、視聴トークン確認・再発行 | ログイン必須 |
| `/l/{視聴トークン}` | 視聴用ページ。プレイヤー、チャット、いいね、視聴者数、配信者名/アイコンを表示 | 配信の公開範囲設定に依存 |

- 「現在配信中のユーザー一覧」ページは作らない。視聴は `/l/{視聴トークン}` への直リンクが前提。
- `/live` は常にログインユーザー本人の配信専用であり、他人の配信の閲覧・管理はできない。

## 2. 配信権限

- 配信を開始できるのは、ロールが `User` 以上(Guest不可)。既存のロール体系(Guest/User/Moderator/Admin/Owner)をそのまま使う。
- 固定ストリームキーを使えるのは、既存の `account_level`(`default`/`trusted`/`creator`/`restricted`)が `trusted` 以上のユーザー。それ未満はランダムキーのみ。
- NSFW/年齢制限が必要な配信内容について、システム側の制御機構は設けない。利用規約の一般条項での対応とする。

## 3. ストリームキー・視聴トークン

- **ストリームキー**(OBSに入力する配信認証情報):
  - デフォルトはユーザーごとのランダム値。
  - `trusted` 以上のユーザーは固定IDに変更可能。
  - ユーザーは自分でいつでも再発行できる。
- **視聴トークン**(`/l/{token}` のtoken部分):
  - ストリームキーとは別に発行する独立した値。ストリームキーの再発行と連動しない。
  - ユーザーは自分でいつでも再発行できる(共有範囲を絞りたい場合や漏洩時に使う)。
  - **設計上の理由**: 視聴用リンクは第三者へ共有されることが前提のため、OBSの認証情報であるストリームキーと同一の値を使うと、視聴リンクの流出がそのまま配信の乗っ取りにつながる。両者を分離することでこのリスクを避ける。

## 4. 公開範囲

配信ごとに配信者が以下の3段階から選択する。

- **公開**: 未ログインユーザーでも `/l/{token}` から視聴可能。
- **フォロワー限定**: ログイン済みかつ配信者をフォローしているユーザーのみ視聴可能。
- **非公開**: 配信者本人のみ視聴可能。

## 5. 配信中の挙動

- 同時配信数: 1ユーザーにつき1配信まで。
- OBSとの接続が切れた場合: 一定時間(目安30秒〜1分、実装時に確定)待機し、再接続がなければ自動的にオフライン扱いにする。時間内に再接続されれば配信を継続する。
- 管理者による個別の強制停止(緊急off)機能は実装しない。問題があった場合は既存のBAN機能で対応する(BANされたユーザーは配信キーが無効化される前提)。
- 画質/ビットレート: サーバー側での再エンコードは行わず、OBSからの入力をそのまま中継する(パススルー)。
- ビットレート上限: システム側で上限を設定し、超過した配信は強制切断する。具体的な上限値は実装時にVPSのスペック・帯域と相談して決定する。

## 6. 配信メタデータ

- タイトル・説明文・ゲーム名・サムネイルなどの付帯情報は持たせない。
- 視聴ページには配信者の名前・アイコンを表示する(匿名配信にはしない)。

## 7. アーカイブ

- 配信終了後の自動録画・VOD化(投稿化)は実装しない。配信終了と同時に映像は残らない。

## 8. チャット

- リアルタイムチャットを実装する。
- 書き込みはログインユーザーのみ(公開配信は未ログインでも視聴は可能だが、書き込みは不可)。
- チャットログは配信終了後も保存する(通報対応の証拠保全のため)。既存のコメント同様の保存・削除ポリシーを想定。
- 既存のNGワード検出機能(`moderation_rules`)をチャットにも適用する。

## 9. いいね・視聴者数

- 配信に対する「いいね」機能を実装する。
- 視聴者数として、現在の同時接続数を表示する。

## 10. モデレーション・通報

- 既存の通報機能(`reports`)を拡張し、`target_type` に配信(ライブストリーム)を追加する。視聴者は配信中の内容を通報できる。
- 通報を受けた場合の対応は既存の管理フロー(管理者確認 → 必要に応じてBAN)を使う。配信専用の強制停止機能は作らない。

## 11. 通知

- 配信開始時、既存のWeb Push基盤を使ってフォロワーに通知を送る。
- 送信対象は配信の公開範囲に応じて絞る(例: 非公開配信では通知しない、フォロワー限定配信ではフォロワーのみ、公開配信でも通知対象はフォロワーとする)。

## 12. インフラ

- ライブ配信用のサブドメイン(例: `live.clipshare.link`)を用意する。DNS設定が必要。
- サーバー全体の同時配信数に上限を設け、超過時は新規配信の開始を拒否する。具体的な上限数は実装時にVPSのスペックと相談して決定する。

## 13. VRChat向け配信(RTSP / MPEG-TS)

TopazChatと同様に、VRChatワールド内の動画プレイヤー(AVPro Video Player)に直接貼り付けて視聴できるURLを、Web視聴(`/l/{token}`)と並行して提供する。

- **配信URLの識別子**: `/l/{token}` と同じ既存の視聴トークンをそのまま使う。専用トークンは発行しない。
  - 例: `rtsp://live.clipshare.link/live/{token}`(PC版VRChat向け)
  - 例: `https://live.clipshare.link/ts/{token}`(Quest等スタンドアロン向け、MPEG-TS)
- **対応プラットフォーム**: PC版(RTSP)とQuest等スタンドアロン(MPEG-TS)の両方に対応する。
- **公開範囲との関係**: RTSP/MPEG-TSにはログインやフォロー関係の判定を掛けられないため、**公開/フォロワー限定/非公開のすべての配信でURLを発行する**。フォロワー限定・非公開でも、この URLを知っている第三者は視聴できてしまう点はユーザーが許容した上での仕様とする。
- **ビットレート**: Web視聴用のパススルー配信(5章)とは別に、サーバー側で**TopazChat相当の低ビットレート(目安: 映像2Mbps・音声320kbps程度、具体的な数値は実装時に確定)へ自動的に再エンコード**する専用出力を用意する。OBS側の設定に関係なく、VRChat向け出力は常にこの上限に収まる。
- **表示場所**: `/live` ページの「視聴リンク」カード内に、Web視聴URLと並べてRTSP URL・MPEG-TS URLを表示する。
- **注意書き**: 公開範囲が「フォロワー限定」または「非公開」のとき、視聴リンクカード内に「このURLは公開範囲に関係なく視聴できます」旨の注意書きを表示する。

この機能により、Web視聴向けパイプライン(パススルーのHLS)とは別に、VRChat向けの常時トランスコードジョブ(サーバー負荷増)が配信ごとに追加で必要になる。

## 14. 実装状況(数値・技術選定の確定分)

以下は実装フェーズで確定した内容。数値は `SiteSetting` テーブル経由で管理画面から変更可能(`lib/live/settings.ts`、既存の`storage_settings`/`quick_share_*`と同じ設計)。

- ビットレート上限: Web用 8,000kbps、VRChat用 映像2,000kbps/音声320kbps(いずれも初期値、admin画面相当のDB設定で変更可能)
- サーバー全体の同時配信数上限: 初期値4(VPSスペックに応じて調整想定)
- OBS切断時の自動オフライン化までの待機時間: 初期値45秒
- RTMP入稿・配信サーバー: MediaMTXを採用(RTMP入稿 → HLS/RTSP/MediaMTX Control APIでの動的パス管理に対応。`scripts/mediamtx.yml.example`、`docs/vps-deployment.md` 参照)
- サブドメイン: `live.clipshare.link`(DNS設定手順は`docs/vps-deployment.md`に記載)
- Prismaスキーマ: `LiveStream`/`LiveSession`/`LiveChatMessage`/`LiveLike` を追加(`prisma/schema.prisma`)
- リアルタイム基盤: `scripts/live-chat-server.mjs`(WebSocket)がチャット・視聴者数・いいね・オフライン自動遷移(定期スイープ)を担当
- 配信キーと視聴トークンの分離: MediaMTX上は入稿パス`live/{streamKey}`と視聴パス`live/{viewToken}`を分け、Next.js側のwebhookがControl API経由で視聴パスを動的に登録/削除する(`lib/live/media-control.ts`)
- VRChat Quest等スタンドアロン向けMPEG-TS出力: 別プロセス`scripts/live-mpegts-relay.mjs`(systemdサービス`clipeshare-live-mpegts`、任意)が視聴パス(`rtsp://127.0.0.1:8554/live/{viewToken}`)をffmpegでVRChat向けビットレート上限に再エンコードし、`https://live.clipshare.link/ts/{viewToken}`でHTTP配信する。視聴者が来るまでffmpegは起動せず(遅延スポーン)、最後の視聴者切断後15秒で停止する。同時に走らせる本数は`LIVE_MPEGTS_MAX_CONCURRENT`で上限を設ける(既定2)。

## 15. UI仕様

配信者向け(`/live`)・視聴者向け(`/l/{視聴トークン}`)のモックアップを作成し、レイアウトを確定した。デザインは既存の `/c/[id]`(投稿詳細ページ)の配色・コンポーネントパターン(ダークテーマ、`--primary`のミントグリーン、`rounded-md border border-border bg-card`のカード、lucide-reactアイコン)をそのまま踏襲する。

### 15.1 `/live`(配信管理ページ)

- レイアウト: メインカラム(プレビュー・視聴者数/いいね・チャットプレビュー)+ サイドカラム(OBS配信設定カード、視聴リンクカード)の2カラムグリッド。`/c/[id]` と同じ `xl:grid-cols-[minmax(0,7fr)_minmax(360px,4fr)]` パターンを流用する。
- ヘッダー: 「ライブ配信」の見出し + 状態バッジ(配信中/オフライン)。
- **配信on/offは完全自動検知**とする。OBSがRTMP接続してきた瞬間に自動で「配信中」になり、切断(または既定のタイムアウト経過)で自動的に「オフライン」に戻る。ページ上のボタンはサイト側からの**手動強制終了**のみで、「配信を開始する」ボタンは置かない(開始はOBS側の操作がトリガー)。
- プレビュー: 配信中は実映像のプレビュー、オフライン時は「OBSからの接続を待っています」等のプレースホルダー。
- 視聴者数・いいね数をメトリクスカードで表示。
- チャットプレビュー: 視聴者に見えるチャットと同じ内容を配信者も確認できる(閲覧のみ、書き込み欄は無し)。
- OBS配信設定カード: ストリームサーバーURL(コピー可)、ストリームキー(マスク表示 + 表示切替 + コピー + 再発行)、trusted以上のみ「固定IDに切り替える」導線。
- 視聴リンクカード: Web視聴URL(コピー可)、公開範囲セレクト(公開/フォロワー限定/非公開)、視聴トークン再発行ボタンに加えて、**VRChat向けのRTSP URL(PC版)・MPEG-TS URL(Quest等)をWebリンクと並べて表示**する。公開範囲が「フォロワー限定」「非公開」のときは、これらのURLが公開範囲に関係なく視聴可能である旨の注意書きを添える(13章参照)。

### 15.2 `/l/{視聴トークン}`(視聴ページ)

- レイアウトも同じく `/c/[id]` 準拠の2カラム: メイン(プレイヤー + 配信者情報 + いいね/通報)+ サイド(チャットパネル、スクロール可能・入力欄付き)。
- プレイヤー: 左上に「LIVE」バッジ、右上に視聴者数バッジ(同時接続数)。
- 配信者情報: アイコン + 表示名を人物としてプレイヤー直下に表示(タイトル等のメタデータは表示しない、11章と整合)。
- いいねボタン: プレイヤー直下、投稿詳細ページの「いいね」ボタンと同じ見た目。
- 通報: アイコンのみを常時表示し、クリックすると**既存の投稿通報と同じフォーム**(理由セレクト + 詳細テキスト)がポップアップする。`/c/[id]` の通報カードと同じ選択肢体系を流用する。
- チャットパネル: メッセージ一覧 + 入力欄。未ログイン時は入力欄の代わりに「コメントするにはログインしてください」の案内文(既存コメント欄と同じ文言パターン)。
- **配信していない状態で `/l/{token}` にアクセスされた場合**は、プレイヤー位置に「現在オフラインです」というプレースホルダーのみを表示する(チャットログや配信者情報などは表示しない)。
- **モバイルレイアウト**: `/c/[id]` と同様に、`xl`未満の画面幅ではグリッドが1カラムに縦積みになる。順序は プレイヤー → 配信者情報(いいね/通報含む)→ チャット。チャット専用のオーバーレイ切り替えUIなどは作らない。
